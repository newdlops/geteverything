# Crawlers Code Review Guidelines

이 문서는 “인터넷에서 정보를 수집하고 앱에 서비스하는” 크롤링 백엔드 프로젝트의 PR/코드리뷰 기준을 정의합니다.

## PR 기본 요건

- PR 설명에 **대상 사이트/기능 범위**, **예시 URL**, **수집 필드(스키마) 변경**, **예상 트래픽/런타임 영향**을 명시합니다.
- 사이트별 **수집 주기/딜레이/동시성**, **프록시/쿠키/세션**, **Selenium 사용 여부**를 명시합니다.
- 운영 반영 시 **롤아웃/롤백** 계획과 “실패 시 안전한 동작”(graceful degradation)을 적습니다.

## 정책·컴플라이언스

- 대상 사이트의 **ToS/robots.txt/접근 정책**을 확인합니다(필요 시 문서/티켓 링크로 근거 남김).
- 로그인/유료/민감 데이터(개인정보 등) 수집은 **명시적 승인** 없이는 금지합니다.
- CAPTCHA/안티봇 우회 등은 법적/정책 리스크가 크므로 **사용 이유, 대안 검토, 운영 통제(레이트/모니터링)**가 PR에 포함되어야 합니다.

## 아키텍처 원칙

- 가능하면 **HTTP 기반(Scrapy) 우선**, **Selenium은 “JS 렌더링이 필수인 경우에만” 제한적으로** 사용합니다.
- 역할 분리:
  - Spider: URL 생성/요청/파싱
  - Item: 스키마(필드 정의)
  - Pipeline: 정규화/검증/저장/발행
  - Utils: 공용 파서/정규화 함수

## 요청·재시도·안정성

- 타임아웃/재시도/백오프가 명확해야 합니다(무한 대기 금지).
- 파싱 예외는 “조용히 삼키지 말고” **URL·원인·샘플 데이터**를 포함해 로깅합니다.
- 중복 수집 방지(안정적인 `article_id`/canonical URL), 페이지네이션 종료 조건이 명확해야 합니다.
- 프록시를 쓸 경우 **신뢰 가능한 공급원**(유료/사내) 사용을 기본으로 하고, 코드/리포지토리에 프록시 리스트를 하드코딩하지 않습니다.

## Selenium 사용 시 필수 체크

- Selenium 적용 범위를 `request.meta` 플래그 등으로 제한해 **모든 요청을 브라우저로 처리하지 않도록** 합니다.
- `driver.get()`에 대한 **page load timeout**을 설정하고, 실패 시 재시도/스킵 정책을 정의합니다.
- 리소스 정리: 스파이더 종료 시 **`driver.quit()`** 및 임시 파일/프로필 정리 정책을 명확히 합니다.
- 스크린샷/HTML 덤프는 컨테이너/서버리스에서 쓰기 가능한 경로(예: **`/tmp`**)를 사용합니다.
- 프록시/쿠키 전략을 문서화합니다(드라이버가 Scrapy의 프록시/쿠키 설정을 자동으로 따르지 않는 점 주의).

## 파싱 품질

- 선택자는 “깨지기 쉬운 인덱스 접근”을 피하고, 필드 누락/마크업 변화에 대한 fallback이 있어야 합니다.
- 텍스트 정규화(공백/이스케이프/HTML 제거)와 숫자·통화·시간대 처리 기준을 통일합니다.
- 값이 없을 때 `None`/빈 문자열 등 **일관된 규칙**을 유지합니다.

## 관측성(로그·메트릭)

- 로그에는 최소한 `spider`, `url`, `stage(list/detail)`, `error_type`이 포함되어야 합니다.
- 수집 성공/실패/스킵 카운트를 집계 가능하게 합니다(운영 시 알람/대시보드 연동 용이).
- 디버그 아티팩트(스크린샷/HTML)는 샘플링하거나 에러 케이스에만 저장해 비용을 관리합니다.

## 보안

- 비밀값(API Key/쿠키/계정)은 코드에 금지, 환경변수/시크릿 매니저로 주입합니다.
- 로그에 토큰/쿠키/개인정보가 남지 않도록 마스킹합니다.
- 외부 입력(URL 등)을 그대로 요청하는 경우 SSRF 관점에서 검증/허용 리스트를 고려합니다.

## 테스트·검증

- 파싱 로직은 가능하면 **HTML fixture 기반 유닛 테스트**로 검증합니다(라이브 사이트 직접 호출 테스트 금지).
- 신규/변경 셀렉터는 “샘플 HTML + 기대 결과”를 PR에 포함하면 리뷰가 빨라집니다.

## Reviewer 체크리스트

- 수집 정책(딜레이/동시성/재시도)과 컴플라이언스 근거가 있는가?
- Selenium/프록시 사용이 “정말 필요한 범위로만” 제한되어 있는가?
- 타임아웃/리소스 정리(quit/임시파일)가 보장되는가?
- 파싱 실패 시 운영에서 원인 추적이 가능한 로그가 남는가?
- 스키마 변경이 파이프라인/다운스트림(앱/API)에 호환되는가?
