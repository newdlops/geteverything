# 고유 상품과 가격 이력

제목과 쇼핑몰 상품·옵션 번호를 결합한 최신 연결 방식은 [상품번호 수집과 연결](MERCHANT_IDS.md)을 참고한다.

상품 UUID는 제목에서 추출한 브랜드·제품명 또는 모델·개별 규격·옵션을 기준으로 만든다. 묶음 개수는 판매 구성으로 분리한다. 제목으로 확인되지 않는 사양은 추정하지 않는다. 자동 상품은 운영자 확인 전 상태로 표시한다.

## 처리 경로

1. PostgreSQL `deals_product_request` 트리거가 신규 글 또는 가격·제목 변경을 작업과 원본 가격 관측으로 보관한다. 조회수·추천수 변경은 가격 이력을 늘리지 않는다.
2. 기존 category worker가 상품 규칙과 가격 계산을 처리한다. 로컬 LLM은 같은 엔진을 한 요청씩 공유하며 브랜드·제품명·모델·옵션을 추출한다. 외부 추론 API는 없다.
3. 제목 근거와 규격이 검증된 결과를 상품 UUID에 연결한다. 다른 용량·모델·옵션, 선택 구성, 혼합 상품을 임의로 합치지 않는다.
4. 운영자의 연결 확인·변경은 동일/다른 상품 학습 예제가 된다. 확인된 제목 별칭은 이후 동일 규격의 묶음 판매에도 재사용한다.
5. CPU용 로지스틱 매칭 모델은 확인된 예제로 가중치를 학습하고, 유사 상품 후보를 정렬한다. 학습 점수만으로 자동 병합하지 않는다. 가격·판매처·묶음 수만 달라진 동일 제목은 규격도 확인한 뒤 추출 결과를 재사용해 반복 추론을 줄인다.

모델 출력의 제품명이 제목에 포함된 일부 단어와만 일치해도 통과시키지 않는다. 크기·수량 앞의 제목 기반 제품 줄 전체를 복원해 하위 제품군이 다른 상품과 합쳐지는 것을 막고, 추출 규약 버전을 캐시 키에 포함한다. 모델 어댑터는 분리된 상품군 검증에서 오병합 0건 등 승격 기준을 모두 만족해야 적용하며, 운영자의 확인 없이 모델의 추측을 학습 정답으로 재사용하지 않는다.

`products-7`부터 제목 끝의 게시판 댓글 수 `[1]`~`[999]`를 상품 옵션에서 제외하고, 가격 괄호에 남은 카드·멤버십 문구와 쇼핑몰명을 상품명·브랜드 근거로 인정하지 않는다. `[1TB]`처럼 규격을 나타내는 표기는 유지한다. 개별 용량·맛·색상·모델은 고유 상품 경계이며 24개·48개 같은 판매 묶음 수는 가격 관측의 수량으로 남긴다. 기존 자동 연결은 새 규칙만으로 일괄 병합하지 않고 제목과 가격 이력의 근거를 확인해 단계적으로 재검토한다.

매일 실행하는 `geteverything-product-quality.timer`는 분류 워커와 별도 컨테이너에서 활성 상품과 연결 글을 읽기 전용으로 검사한다. 댓글 수가 상품 옵션에 들어간 글, 같은 규격인데 숫자 옵션만 달라 갈라진 상품, 동일한 정규화 서명, 쇼핑몰 브랜드 오인, 판매 묶음 수가 다른 동일 상품을 집계하고 검토할 후보 UUID를 기록한다. 이 결과는 학습 정답이 아니다. 관리자가 연결과 추출값을 확인한 정답만 매칭 모델과 다음 LoRA 학습에 들어간다. 상품군·옵션별 상위 묶음은 별도 검증 집합을 확보한 뒤 정확한 고유 상품과 구분해 제공한다.

웹 어드민 배포 후, 오답을 발견하면 **게시물 상품 연결**에서 상품을 바로잡고 `LLM 학습 정답으로 저장`을 선택해 브랜드·제품군·모델·옵션·대분류도 제목을 근거로 확인한다. 체크한 정답만 모델 출력과 분리해 저장하고, 같은 필드를 게시물 추출 정보에도 반영한다. 제목에 없는 값은 검증에서 거부한다. 새 운영자 정답이 16건 이상 쌓이면 예정된 학습 점검에서 새 LoRA 후보를 만들고, 별도 보류 상품군 평가가 승격을 결정한다.

`products-4`는 인식 가능한 CPU·모니터의 완전한 모델 번호를 기준으로 브랜드와 고정 사양을 정규화한다. 행사 날짜, CPU 세대 설명, 주사율 표기 여부로 별도 상품을 만들지 않는다. SSD 용량과 리퍼·중고 여부는 구분한다. PC 본체·부품 조합·여러 모델을 광고하는 글은 단품 가격에 연결하지 않는다. 음료의 맛·개별 용량·용기 표기는 상품명에도 표시하며 제목에 없는 용기나 맛은 추정하지 않는다.

LLM 추출, 제목 별칭 재사용, 매칭 모델 학습, LLM 가중치 미세학습은 별도 기능이다. 가벼운 매칭 모델의 초기 예제는 검토한 제목 쌍과 구성한 반례 64건이며 운영 정확도 표본이 아니다. 상품군을 나눠 52건 학습·12건 검증한다. 운영자 예제가 쌓이면 최대 최근 2,000건으로 매시간 확인해 재학습하며, 같은 데이터는 같은 학습 버전을 재사용한다. 모델 자체 추측은 정답 데이터로 넣지 않는다.

사용자가 선택한 정책에 따라 같은 상품의 24캔·48캔은 같은 UUID로 연결하고 캔당 가격을 비교한다. 로컬 LLM 자체의 미세학습도 포함한다. Qwen3.5 2B 마지막 블록의 Q/K/V/O attention과 gate/up/down MLP에 rank 16 LoRA를 적용한다. 학습한 어댑터가 추론 시 유효 가중치에 더해진다. [Hugging Face LoRA 문서](https://huggingface.co/docs/peft/en/package_reference/lora), [강화 학습 구성과 운영 기록](TRAINING_INTENSIVE.md) 참조.

현재 LLM 정답 데이터 488건은 상품군 기준으로 학습 388건·검증 100건을 분리한다. 검증에는 24개 상품군과 단일 상품으로 연결하면 안 되는 28건이 포함된다. 같은 상품의 묶음·판매처 변형은 양쪽에 중복되지 않는다. 이전 검증 상품군도 계속 검증 쪽에 둔다. 운영자가 기존 자동 연결을 확인하면 제목에 근거가 있는 추출값만 추가 정답이 된다. 다른 상품으로 변경했지만 필드 정답을 확인할 수 없는 경우에는 연결 쌍만 학습하고 LLM 정답을 만들어내지 않는다.

2026-09-24 운영 상태에서 활성 LoRA는 학습 388건·분리 검증 100건으로 승격됐고, 구성된 검증에서 100/100 정답·오병합 0건이었다(기존 모델 73/100). 이 자료에는 실제 운영자 추출 교정이 0건 포함되어 있어, 이 점수는 운영 실데이터 정확도가 아니다. 어드민 교정 입력을 통해 운영에서 확인한 정답을 모은 뒤 다음 학습 후보에 포함한다.

## 조회·수정

- 어드민 **고유 상품 → 게시물·가격 이력 보기**: 기간, 통화, 판매 구성/낱개/100g/100ml, 배송비 포함 선택.
- **고유 상품 → 로컬 LLM 미세학습**: 전처리·가중치 학습·비교 평가의 단계별 진행률, 검증 정답 수, 이번 가중치의 운영 반영 여부. 검색 조건을 유지하는 새로고침으로 최신 기록을 조회한다. 10분 이상 기록이 없거나 자원 보호로 대기 중이면 별도 안내한다.
- **게시물 상품 연결**: 연결 상품을 선택하고 저장하면 현재 제목 세대를 확정한다. 제목이 달라지면 이전 가격은 이전 상품에 남으며, 수동 연결은 다시 확인하도록 표시한다.
- **상품 연결 학습 예제**: 확인 출처와 동일/다른 상품 라벨. 목록 작업으로 즉시 재학습 가능.
- **상품 매칭 학습 결과**: 실제 가중치 학습 버전과 검증 집계.
- `GET /api/deals/`: `product_id`, `product_status` 추가.
- `GET /api/products/?q=검색어`, `GET /api/products/{UUID}/`, `GET /api/products/{UUID}/history/?start=2026-01-01&end=2026-09-19&currency=KRW&basis=item`.

가격 이력은 100건씩 페이지로 조회한다. 통화나 단가 기준을 혼합하지 않으며, 조건부 금액과 수량이 불확실한 단가는 그래프에서 제외한다. 환율을 과거 가격에 소급 적용하지 않는다. 기존 글은 현재 DB에 남아 있는 가격 한 시점만 복원하고, 게시물 작성일과 실제 가격 확인 시각을 각각 공개한다.

## 운영

기존 worker 환경에서 실행한다. 자격증명은 기존 root 전용 env 파일을 사용하며 출력하지 않는다.

```sh
python -m gadmin.products.manage status
python -m gadmin.products.manage batch --limit 50
python -m gadmin.products.manage seed-examples
python -m gadmin.products.manage train
python -m gadmin.products.manage export --output /tmp/reviewed-product-pairs.jsonl
python -m gadmin.products.manage sft-export --output /tmp/reviewed-product-extraction.json
python -m gadmin.products.manage deduplicate
python -m gadmin.products.manage deduplicate --apply --backup /repair/products-before.json
python -m gadmin.products.manage backfill-status
python -m gadmin.products.manage backfill-step --limit 100
```

`deduplicate`의 기본 동작은 변경 예정 집계다. 적용에는 새 백업 파일 경로가 필요하며 파일이 이미 있으면 덮어쓰지 않는다. 운영에서는 자원 제한이 있는 일회성 컨테이너와 root 전용 백업 디렉터리를 사용한다. 이 작업은 운영자 확인·수동 연결·연결 학습 예제가 있는 상품을 보존한다. 상품 UUID를 삭제하지 않고 중복 UUID를 대표 상품으로 연결하며, 어드민과 API 목록에는 활성 상품만 표시한다. 예전 상품 조회 주소와 가격 이력 주소는 대표 상품으로 이어진다.

`deduplicate --product-id UUID`는 선택한 상품만 재평가한다. 같은 정규화 제목의 서로 다른 연결은 제목에서 확인한 용량·맛·모델·용기 속성이 모두 일치할 때만 통합한다. 정보가 부족하거나 기존 링크가 모순되면 보존한다. 상품 등록 잠금 아래 현재 게시물과 가격 관측을 함께 이동하고, 계산된 가격 데이터의 해시가 달라지면 전체 트랜잭션을 되돌린다. 선택 범위 수리 뒤에는 백업 경로와 `price_payload_preserved`를 확인한다.

가격 관측은 각 기록의 당시 제목으로 재검증한다. 현재 제목의 상품을 과거의 다른 상품 가격에 일괄 적용하지 않는다. 원본 가격 입력·계산값·시각의 해시가 변경되면 트랜잭션을 롤백한다. 자동 생성, 수동 연결, 통합 작업은 상품 등록 잠금 → 게시물 연결 → 상품 → 가격 순서로 처리한다. 초기 버전용 `repair` 명령은 중복 통합 용도로 사용하지 않는다.

초기 백필은 15초마다 최대 50개씩 가격 관측과 작업을 만든다. 로컬 모델 대기열은 40개, 나머지는 분석 대기 상태이며 신규 게시물을 우선한다. 처리 중 수정된 제목·수동 연결은 revision 비교로 늦은 응답을 거부한다. PostgreSQL과 작업자의 잠금 순서를 일치시키고, 모델 응답을 기다리는 동안 DB 트랜잭션을 잡지 않는다.

상품 연결 백필은 가격 관측 생성과 별도로 `products:identity-backfill:<처리 버전>`에 진행 상태를 보관한다. 기존 미연결 대기·검토 작업을 현재 규칙으로 한 번씩 다시 확인하고, 실행 가능한 규칙 대기열은 200개로 제한한다. 같은 정규화 제목·규격에서 연결 결과가 하나로 확정된 모델 응답은 최대 100개씩 재사용한다. 수동 연결·유효한 처리 임대·다른 제목 세대의 가격은 덮어쓰지 않는다. 재시작 시 DB 상태에서 이어가며, `rules_checked`는 규칙 확인 수, `linked`는 실제 연결 수다. 규칙 통과가 끝나도 모델 대기가 남으면 완료로 표시하지 않는다.

`products-5`는 음료의 용기 표기 누락을 부분 정보로 처리한다. 브랜드·상품명·맛·용량·그 밖의 규격이 같고 등록된 용기가 하나뿐이면 `코카콜라 190ml`을 `코카콜라 190ml 캔`에 연결한다. 용기 정보가 처음 추가되면 기존 UUID를 유지하며 보완한다. 제목에서 직접 확인한 속성은 그대로 남긴다. 캔·페트·유리병 등 명시된 용기가 다르거나 후보 용기가 여러 종류면 추정해서 합치지 않는다. 기존 이력도 `deduplicate`로 같은 기준을 적용하며, 서로 충돌하는 용기가 확인된 경우 기존 추정 연결을 다시 분리할 수 있다.

모델 한도는 0.20 CPU/3 GiB다. 2 vCPU 호스트의 CPU 60% 미만·가용 메모리 4 GiB 이상 관측 2회 후 시작하고, CPU 80% 이상 또는 가용 메모리 3 GiB 미만이면 중지한다. 2026-09-20 브라우저 효율화와 함께 조정한 기준이다. 요청은 최대 240초, 임대는 300초다. 초기 실데이터에서 배송 문구를 브랜드로, 수량을 모델/옵션으로 해석한 출력을 발견해 `product-extract-2`의 예제와 검증 규칙을 추가했다. `35gx20개`와 LG `32GX870B`의 단위/모델 혼동도 구분한다.

미세학습은 서버 또는 [운영자 Mac](LOCAL_TRAINING.md)에서 실행할 수 있다. Mac에서는 같은 캐시·체크포인트를 이어 학습한 뒤 서버의 `runner.py --evaluate-only`로 가져와 검증한다. 공식 체크포인트를 고정 revision과 체크섬으로 받은 후 학습은 네트워크 없이 동작한다. 서버 학습은 0.35 CPU/6 GiB 한도이며 기존 추론과 번갈아 자원을 사용한다. 규칙 처리·가격 기록·크롤러는 계속 실행된다. 가용 메모리 3 GiB 미만이면 서버 학습을 중지하고, 호스트 CPU 80% 이상이 연속 2회 관측되면 일시정지한다. CPU 65% 미만에서 재개한다. 체크포인트와 고정 계층 캐시를 재사용한다.

타이머는 한국 시간 02:30에 새 정답을 점검한다. 같은 데이터·학습 설정의 완료 작업은 반복하지 않으며 새 운영자 정답 16건 이상 또는 검토 예제·학습 설정 변경 시 다음 학습을 시작한다. 실패는 같은 데이터·설정에서 최대 3회까지만 시도한다. 최대 4 epoch/1,200 step이며 초기 246건은 984 step이다. 매 epoch 검증 손실을 확인해 가장 좋은 체크포인트를 보관하고 2회 연속 개선이 없으면 조기 종료한다. 학습·생성 평가 단계는 각각 18시간·4시간, 서비스 전체는 24시간으로 제한한다. 완료한 최근 두 실행과 활성 모델을 보관하며, 참조 없는 오래된 캐시는 정리한다. 로그는 컨테이너당 2 MiB × 2개로 제한한다.

학습 완료 후 같은 버전의 공식 llama.cpp 도구로 GGUF LoRA를 변환한다. 검증 정답률 80% 이상이며 기존 모델보다 정답 수가 늘고, 기존 정답 회귀·혼합 상품의 단품 오인·서로 다른 상품의 병합이 없어야 한다. 같은 상품의 분리 오류는 기존 모델보다 늘어나면 안 된다. 응답 형식·지연·검증 손실 기준도 모두 통과해야 반영한다. 상품 추출 요청에만 어댑터를 적용하므로 카테고리 단독 분류는 기존 모델을 사용한다. 반영 실패 시 이전 설정으로 복원한다. 구성한 학습·검증 예제로 전체 서비스 정확도를 주장하지 않는다.

진행 상태는 서버의 `/var/lib/geteverything-product-training/status.json`, `evaluation.json`, `active.json` 및 DB `ClassificationState`의 `products:llm_training`에 저장한다. `probe_complete`는 소량 시험 완료이며 전체 학습·운영 반영 완료를 의미하지 않는다. 운영 반영 여부는 `active.json`과 `promoted` 값으로 확인한다.

`caching_frozen_layers`는 학습에 재사용할 고정 계층 출력을 만드는 단계이며 `cached/total_cache`로 진행률을 확인한다. 이어서 `training`에서 실제 LoRA 가중치를 갱신한다. 서비스는 oneshot이므로 작업 중 systemd의 `ActiveState=activating`은 정상이다. 초기 시험에서는 가중치 변경·GGUF 변환·요청별 어댑터 적용을 확인했으며, 초기 전체 작업은 서버에서 비동기로 실행한다.

스키마 `deals.0013_product_canonical_aliases`와 웹을 먼저 적용한 다음 작업자를 배포한다. `is_active`에는 DB 기본값도 두어 배포 중 이전 작업자의 INSERT를 지원한다. 기존 크롤러와 썸네일 작업자는 재시작할 필요가 없다. 작업자 롤백은 배포 기록의 이전 runtime.json/이미지로 복원한다. 통합 이후에는 활성 상품·별칭을 이해하는 버전을 유지하며 스키마나 이력 테이블을 삭제하지 않는다.
