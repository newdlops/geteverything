첫 적용에서 크롤러 tmpfs의 noexec 때문에 ChromeDriver 실행이 실패한 문제를 수정했다. FlareSolverr 0.5 CPU 제한에서는 아카라이브 처리 시간 초과가 발생해 최종적으로 0.75 CPU로 조정했다. 최종 설정에서 동일 요청들이 약 16~18초 안에 연속 성공했다.

## 뽐뿌 403 추가 진단 — 2026-09-14 KST

운영 로그의 00:16 및 00:30 실행에서 목록 1~5페이지 모두 403이었다. Scrapy가 해당 응답을 무시하므로 목록 파서와 상세 수집까지 도달하지 않는다. 자식 프로세스는 이때도 `exit=0`으로 종료하므로 프로세스 종료 코드만으로 수집 성공을 판단할 수 없다.

로그인·쿠키 없이 현재 크롤러의 URL과 헤더를 그대로 읽어, 공개 목록 1페이지를 다음과 같이 제한적으로 비교했다.

| 접속 환경 | HTTPS 결과 |
| --- | --- |
| 로컬 Mac의 Python 요청 | 200, `뽐뿌 - 뽐뿌게시판` 제목과 `bbs_new1` 목록 포함 |
| 크롤링 서버 컨테이너의 Python 요청 | 403, 571바이트의 `403 Forbidden` / `nginx/1.12.1` 오류 페이지 |

관찰한 서버 오류 페이지에는 Cloudflare 챌린지나 CAPTCHA 표시가 없었다. 로컬·서버에서 조회된 IPv4 주소 집합은 같았다. HTTP 주소도 각 환경에서 한 번씩 비교했지만, 로컬은 115바이트 본문, 서버는 빈 본문이어서 200 상태만으로 목록 접근 성공으로 볼 수 없었다.

이 결과는 크롤링 서버 IP 또는 오라클 대역에 대한 접근 제한을 강하게 시사한다. 실제 적용된 차단 규칙과 개별 IP 차단인지 대역 차단인지는 뽐뿌 측 확인이 필요하다. 서버에서 일반 Chromium으로 요청해도 실패했으므로 단순히 Selenium으로 전환하면 해결된다고 볼 근거는 없다. IP 허용 여부를 사이트 운영자에게 확인하는 것이 다음 조치이며, 이번 진단에서 외부 문의를 보내지는 않았다.

운영 크롤러 설정은 변경하지 않았으며 기존 600초 간격을 유지했다. 진단용 Chromium은 확인 후 종료하고 별도 임시 프로필을 정리했다.

### 기존 수집 방식과 추가 비용 없는 경로 검증

- 운영 컨테이너의 실제 소스를 확인했다. FMKOREA는 `SeleniumMiddleware`, ARCA는 `FlareSolverrMiddleware`만 활성화돼 있다. 두 사이트의 회전 프록시 미들웨어는 주석 처리돼 있으며, 코드에 남은 프록시 목록은 사용되지 않는다. 크롤러·FlareSolverr 컨테이너에 프록시 환경변수도 없었다.
- 보관한 로그 마지막 부분에서 뽐뿌 HTTP 200 응답 305회를 확인했다. 마지막 표본은 2026-05-04 00:49:21 KST의 목록 5페이지 요청이다. 다만 상태 코드만으로 저장 성공을 확인할 수는 없다. 이번 진단 전 DB의 PPOMPPU 데이터는 12,892행이며 마지막 갱신은 2026-02-13 03:58:15 UTC였다.
- 현재 서버에서 FMKOREA의 실제 Selenium 설정과 ARCA의 실제 FlareSolverr 경로로 각각 한 번 확인해도 오류 페이지가 반환됐다. 두 래퍼 모두 200/성공 표시를 반환했지만 HTML 제목은 `403 Forbidden`이고 게시글 목록은 없었다. 모바일 목록과 불필요한 쿼리 파라미터를 제거한 PC 목록도 403이었다.
- 프로젝트의 기존 웹 서버 `158.180.67.53`에서도 공개 목록 요청 1회가 403이었다. 해당 서버 설정은 변경하지 않았다.
- 로컬 Mac에서 읽은 [뽐뿌 robots.txt](https://www.ppomppu.co.kr/robots.txt)는 `User-agent: *`, `Allow: /zboard/`를 포함했다. 이 파일이 사이트의 모든 접근 정책이나 개별 IP 제한을 설명하지는 않는다.

현재 Mac의 네트워크를 출구로 사용하는 임시 SSH 포워딩을 검증했다. 서버에는 `127.0.0.1:19443`만 열고, Mac에서 `www.ppomppu.co.kr:443`으로 연결했다. 서버 Python이 원래 도메인의 인증서를 검증하며 HTTPS 요청을 보냈고, 목록 200 응답·25개 행을 받았다. 기존 뽐뿌 파서는 해당 HTML에서 상세 요청 21개를 생성했다.

- 게시글: `733984` / DB article_id `ppompu733984`
- DB PK: `130043`, community_name `PPOMPPU`
- 게시 시각: 2026-09-13 15:57:00 UTC
- 저장·갱신 시각: **2026-09-13 16:01:10 UTC / 2026-09-14 01:01:10 KST**

이 검증은 접속 경로를 바꾸면 기존 파서·저장 로직으로 수집할 수 있음을 보여준다. 개별 IP와 호스팅 대역 중 어떤 차단 규칙이 적용됐는지는 사이트 측 확인 없이는 확정할 수 없다. **자동 수집을 상시 복구한 상태는 아니다.** 사용자는 PC 경유 없이 서버만으로 상시 운영하도록 명시했다. 검증용 SSH 연결은 종료했으며 Mac 경유를 자동 수집에 도입하지 않았다.

## 목록 갱신·순환 보완과 뽐뿌 자동 수집 복구

이전 21회 실패는 당시 상태 검사 결과이며 모든 무료 VPN이 차단됐다는 근거는 아니다. 추가 비교에서 **같은 VPN `121.179.32.138`의 curl 요청이 `Accept-Encoding: identity`이면 403·571바이트, `--compressed`이면 200·정상 목록**이었다. Python도 `Accept: */*`, `Accept-Encoding: gzip, deflate` 등 정상 요청 헤더로 바꾸면 200이었다. 기존 검사가 사용할 수 있는 경로를 실패로 판정한 문제를 확인했다.

상태 검사에 압축 지원 헤더와 gzip/deflate 해제를 적용하고, 잘못된 검사에서 쌓인 제외 목록을 한 번 초기화했다. Spider의 목록·상세 요청에도 동일한 헤더를 적용했다. 상세 요청이 기본 Scrapy User-Agent로 달라지지 않게 했지만, User-Agent 자체가 실패 원인이었다고 단정하지는 않는다.

사용자가 요청한 VPN 목록 관리도 보완했다.

- **5분마다 공식 목록 갱신:** 정상 VPN 유지 중과 재시도 대기 중에도 최신 목록을 받아 갱신 시각·해시·국가별 수·추가/제외 수를 기록한다. 유효한 공개 IPv4 후보를 국가 제한 없이 포함한다.
- **미시험 후보 우선 순환:** 시도 이력을 30일 보관한다. 점수 상위 후보의 대기 시간이 끝나더라도 전체 미시험 후보를 먼저 방문한다. 모두 확인한 뒤에는 가장 오래전에 시도한 후보부터 다시 검사한다.
