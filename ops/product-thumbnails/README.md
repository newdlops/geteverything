# 상품 이미지와 90일 정적 보관

크롤러가 완전한 판매처 링크와 대체 썸네일을 `deals`에 저장하면 같은 트랜잭션에서 `thumbnail_requests`에 이미지 작업이 등록된다. 웹 서버의 상시 작업자가 DB 커밋 알림을 받아 판매 페이지의 대표 이미지를 JPEG로 저장하고 기존 API의 `thumbnail`을 정적 URL로 갱신한다. 크롤링 콜백에서는 이미지 다운로드·변환을 수행하지 않는다. `deals.0008_thumbnail_requests` 마이그레이션이 작업 테이블과 트리거를 설치한다.

## 신규 크롤링 직후 작업

- 게시물 INSERT와 상품 링크·원문 주소 변경을 DB 트리거가 포착한다. 각 사이트의 저장 코드가 작업 등록을 따로 호출할 필요가 없다. 저장이 롤백되면 작업도 남지 않는다.
- 게시물당 대기 요청은 1개로 합치고 변경마다 새로운 revision을 부여한다. 요청을 로컬 영속 큐에 반영한 뒤 같은 revision만 확인 완료 처리하므로 처리 중 새 요청이 들어와도 유실되지 않는다.
- PostgreSQL `LISTEN/NOTIFY`로 커밋 직후 작업자를 깨운다. 알림을 놓치거나 작업자가 재시작해도 요청 테이블에서 복구하고, 알림이 없을 때도 최대 5초 간격으로 확인한다. 알림 수신과 이미지 다운로드 완료는 구분한다.
- 신규 수집의 이미지 생성이 백필보다 우선이다. 한 이미지 처리를 마칠 때마다 새 요청을 다시 확인한다. 이미 실행 중인 이미지 요청은 제한된 시간 안에 마친 뒤 다음 신규 작업을 처리한다. 기존 이미지의 판매처 재시도보다 이미지가 없는 신규 게시물을 먼저 처리한다.
- 조회수·추천수·동일 링크 재저장과 작업자의 썸네일 URL 갱신은 새 작업을 만들지 않는다. 추적 토큰만 바뀌면 요청을 받더라도 동일 상품의 정상 파일과 TTL을 유지한다. 크롤러의 `update_at`은 이미지 처리 때문에 변경하지 않는다.
- 도메인 길이·빈 라벨 등 잘못된 주소를 요청 전에 거부한다. 한 게시물의 예상하지 못한 데이터 예외는 해당 작업의 실패로 기록해 다른 게시물을 계속 처리한다. 실패 상한은 3회이며 디스크·DB·메모리 자체의 장애는 서비스 오류로 드러낸다.

## 이미지 선택

1. 상품 링크의 알려진 리디렉션 파라미터를 풀고, HTTP 리디렉션을 최대 3번 따라간다.
2. 판매 페이지의 JSON-LD `Product`/`ProductGroup.image`, 상품 `itemprop=image`, Open Graph/Twitter 이미지, 상품 본문 이미지 순으로 후보를 평가한다. 상품명 일치도를 반영하고 추천 상품 목록·헤더·로고·배너·추적 픽셀을 제외한다.
3. 최대 3개 후보의 실제 이미지 형식·크기·비율을 검사하고 긴 변이 최대 480px인 JPEG로 변환한다. EXIF 등 원본 메타데이터는 새 파일에 복사하지 않는다.
4. 판매 페이지가 차단되거나 적절한 이미지가 없으면 게시글의 썸네일을 저장한다. 대체 이미지에는 `community_fallback` 출처를 기록하며 판매처를 최대 3번까지 시도한다. 매번 이미지 만료일을 연장하지 않는다.
5. 기존 썸네일도 없거나 다운로드에 실패하면 원문 본문의 이미지와 주변 상품명 설명을 확인한다(`community_body_v2`). 첫 구매·신규 가입 쿠폰을 제외하고 상품명과 가까운 후보를 우선한다. 모든 후보가 실패하면 기존 값은 보존하고 작업 실패를 기록한다.

공개 상품 정보에 기반한 규칙 방식이며 외부 AI API·추가 브라우저·프록시 회전을 사용하지 않는다. 차단된 판매처나 JavaScript 실행 후에만 이미지를 제공하는 판매처에서 직접 수집 성공을 보장하지 않는다. 지원 근거: [상품 구조화 정보](https://schema.org/Product), [Pillow 이미지 처리](https://pillow.readthedocs.io/en/stable/reference/Image.html).

## 저장과 만료

- 운영 공개 주소: `http://158.180.67.53:8001/media/thumbnails/<만료일>/<만료시각>-<해시>.jpg`.
- 영속 파일: 웹 서버 `/var/lib/geteverything-thumbnails/objects`. 웹 컨테이너는 이 디렉터리를 읽기 전용으로 마운트하고 기존 uWSGI가 정적으로 제공한다. 배포·컨테이너 재시작 때 파일을 잃지 않는다.
- 작업 상태: `/var/lib/geteverything-thumbnails/queue.sqlite3`. 작업 컨테이너만 쓰며 웹에 노출하지 않는다. 신규 DB 요청을 즉시 전달받는다. 복구용 보조 점검으로 최초 실행은 최신 500개, 이후 새 ID와 최근 갱신 300개를 약 60초마다 확인한다.
- **TTL은 저장 시점부터 90일**이다. 조회·재크롤링·동일 대체 이미지 재시도는 만료일을 늘리지 않는다. 만료 시 해당 정적 URL을 가리키는 DB 필드부터 비우고 파일을 삭제한다. 다른 썸네일로 변경된 레코드는 지우지 않는다. 만료 정리는 각 작업 실행 시 처리하므로 실행 주기만큼 지연될 수 있다.
- `THUMBNAIL_TTL_DAYS` 기본값은 `90`이며 1~365일을 허용한다. 변경은 이후 저장하는 파일부터 적용한다. 브라우저 캐시는 1시간이며 파일 보관 TTL과 별개다.
- 파일은 임시 파일에 쓴 후 원자적으로 교체한다. 해시 파일명과 만료 시각을 사용해 기존 파일 캐시와 충돌하지 않는다. 파일 저장 후 DB 갱신 실패는 이미지 재다운로드 없이 재시도한다.

## 자원·접근 제한

이미지 작업은 웹 서버에서 메모리 192MiB, CPU 0.25개, PID 64개 제한의 별도 상시 컨테이너로 실행한다. 루트 파일시스템은 읽기 전용이며 UID/GID 65534, 권한 제거, 16MiB 임시 디렉터리를 사용한다. 기존 크롤러 자원·VPN·FlareSolverr 설정은 유지한다.

상시 작업자는 최대 12개·새 작업 시작 예산 55초 단위로 처리하고 다음 요청을 기다린다. 신규 작업이 대기 중이면 대기 시간을 생략한다. 만료·백필 대상 조회·복구 점검은 약 60초 간격이다. 이전 분 단위 타이머는 비활성화한다. 서비스는 실패 시 15초 후 재시작하며 5분 내 3회 실패하면 멈춰 오류를 드러낸다. 상품 페이지 작업은 22초, 대체 이미지 요청은 8초, 원문 본문 확인은 12초로 제한한다. HTML 2MiB·이미지 4MiB, 최대 800만 픽셀, 결과 160KiB 제한을 둔다. 저장소 여유가 2GiB 미만이거나 현재 등록된 이미지 합계가 5GiB를 넘으면 새 파일 저장을 중단한다. 대체 후 만료 대기 중인 이전 파일은 합계에 포함되지 않으므로 실제 디스크 여유도 함께 검사한다.

## 기존 게시물 백필

```sh
sudo python3 /usr/local/lib/geteverything-thumbnails/run.py --start-backfill
sudo python3 /usr/local/lib/geteverything-thumbnails/run.py --status
```

`--start-backfill`은 한 번의 전체 점검을 등록하며 같은 명령을 다시 실행해도 진행 위치나 실패 횟수를 초기화하지 않는다. 최초 등록이 필요하면 상시 서비스를 잠시 정지한 상태에서 실행하고 서비스를 다시 시작한다. 이미 등록한 백필은 상시 작업자가 자동으로 이어서 실행하므로 PC나 SSH 접속 유지가 필요 없다. 배타 잠금은 이중 이미지 처리를 막으며 `--status`는 실행 중에도 읽기 전용으로 진행 상태·마지막 요청·마지막 처리 결과를 출력한다.

1. 시작 시점의 최대 게시물 ID를 고정하고, 빈 썸네일·잘못된 형식의 주소부터 최신순으로 처리한다(`missing`).
2. 나머지 기존 게시물을 최신순으로 점검한다(`all`). 정상 정적 파일은 URL·만료일을 유지한다. 파일이 없거나 저장 크기와 다르면 다시 수집한다. 외부 이미지는 판매처 확인과 대체 이미지 다운로드를 거쳐 정적 저장소로 옮기므로 외부 주소가 존재해도 실제 파일이 깨진 경우 복구 대상이 된다.
3. 판매처와 기존 썸네일이 모두 실패하면 지원하는 5개 커뮤니티의 원문 본문에서 이미지를 찾는다. 메뉴·댓글·사이트 로고용 메타데이터를 제외하고, 이미지가 속한 문단의 첫 구매·가입 쿠폰 안내와 주변 상품명 설명을 반영한다. 이 추가 요청은 12초 안에서 후보 3개까지만 확인한다.
4. 모든 ID를 확인한 뒤 남은 수집·재시도·DB 반영을 기다리고(`draining`), 처리가 끝나면 `complete`로 기록한다. 차단·삭제 등으로 실패한 게시물은 실패로 남으므로 `complete`가 모든 이미지의 복구 성공을 뜻하지는 않는다.

한 번에 최대 50개만 조회하고 미처리 백필이 50개 쌓이면 새 등록을 멈춘다. 이미 저장된 이미지의 일회성 품질 재검토는 기존 작업을 다시 열므로 이 수를 일시적으로 넘을 수 있다. ID 커서는 영속 SQLite에 저장하며 OFFSET이나 전체 게시물 메모리 적재를 사용하지 않는다. 신규 이미지 작업의 남는 처리 시간을 백필에 사용하며 같은 컨테이너 제한을 공유한다. 큐는 메모리 캐시 2MiB, 파일 크기 상한 약 256MiB를 둔다. 실패는 최대 3회이며 같은 백필의 커서 재처리나 중복 실행은 재시도 상한을 초기화하지 않는다.

상태의 `jobs`는 등록된 백필 수, `saved`는 DB에 반영된 유효 정적 이미지 수, `active`는 남은 수집·재시도·반영 수, `counts`는 작업 상태별 수다. `scanned`에는 누락 우선 단계와 전체 점검 단계에서 같은 게시물을 각각 확인한 수가 포함된다. 아직 커서가 방문하지 않은 게시물은 `jobs`와 `active`에 포함되지 않는다. 새로 복구한 이미지는 저장일부터 90일이며, 점검이 끝난 뒤 만료된 옛 게시물을 자동으로 무한 재수집하지 않는다.

초기 본문 선택 방식(`community_body`)으로 저장된 이미지는 개선된 방식으로 한 번 재검토한다. 재시도 상한은 유지하며 같은 이미지가 다시 선택되면 파일·URL·기존 만료일을 그대로 사용한다. 다른 상품 이미지로 교체할 때는 새 파일의 90일 TTL을 적용한다.

## 실행·점검

`/etc/geteverything-thumbnails/worker.env`는 root 전용 600 파일이다. 기존 웹 서비스의 DB 설정과 아래 값을 사용한다. 비밀번호는 이미지나 저장소 문서에 넣지 않는다.

```text
DJANGO_SETTINGS_MODULE=gadmin.admin.settings
THUMBNAIL_PUBLIC_BASE_URL=http://158.180.67.53:8001/media/thumbnails/
THUMBNAIL_TTL_DAYS=90
```

```sh
sudo systemctl status geteverything-product-thumbnails.service
sudo systemctl start geteverything-product-thumbnails.service
sudo journalctl -u geteverything-product-thumbnails.service --since '-15 minutes' --no-pager
```

호스트 `/usr/local/lib/geteverything-thumbnails/run.py`는 현재 `django_django` 이미지로 작업을 실행한다. 신규 서버에서는 정적 디렉터리와 환경 파일을 준비하고 DB 마이그레이션 후 `run.py`와 이 폴더의 systemd 서비스를 설치·활성화한다. 이전 타이머는 사용하지 않는다. `objects` 마운트와 static-map은 저장소의 웹 Compose 오버라이드 및 `gadmin/uwsgi.ini.template`에도 반영했다. 배포 워크플로는 마이그레이션과 서비스 파일 갱신 후 작업자를 재시작해 새 이미지로 실행한다.

크롤러 공통 파이프라인은 재수집 시 썸네일을 덮어쓰지 않으며 변경 필드만 SQL에 저장한다. FMKOREA의 새 레코드에는 기존 썸네일을 사용하되 기존 레코드에는 유지한다. 상품 링크는 실제 `href`를 우선한다. 커뮤니티 내부의 중계 링크이며 표시된 텍스트가 완전한 외부 URL인 경우에는 그 외부 URL을 사용한다. 줄어든 텍스트는 사용하지 않는다. 쿨엔조이의 이미지 `href` 오용도 `src`/지연 로딩 속성으로 수정했다.
